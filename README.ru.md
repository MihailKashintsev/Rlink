# Rlink

**[English](README.md) | Русский**

Rlink — кроссплатформенный мессенджер, построенный вокруг двух идей, которые большинство мессенджеров не воспринимают всерьёз: чтобы написать человеку рядом, не должен быть нужен интернет, а чтобы иметь идентификатор в приложении — не должен быть нужен номер телефона.

- **Bluetooth-mesh и relay-сервер работают вместе.** Сообщения расходятся по соседним устройствам через BLE (и Wi-Fi Direct на Android), когда интернета нет, и уходят через WebSocket-relay, когда он есть. Relay никогда не видит текст сообщений — это zero-knowledge пересыльщик и офлайн-почтовый ящик, а не сервер, который читает переписку.
- **Без номера телефона.** Идентификатор — это пара ключей Ed25519, сгенерированная на устройстве. Контакты добавляются через QR-код или ссылку-приглашение, а не через передачу номера телефона серверу.
- **End-to-end шифрование**, включая собственную реализацию Double Ratchet (forward secrecy + post-compromise security) для личных чатов, сверку кодов безопасности и шифрованную сигнализацию звонков.
- **Работает везде**: Android, iOS, Windows, macOS, Linux и web из одной кодовой базы на Flutter.

Это проект одного разработчика, который активно развивается — рассчитывайте на шероховатости, и посмотрите [известные ограничения](#известные-ограничения), прежде чем считать, что какая-то функция работает так же зрело, как в больших мессенджерах.

## Почему mesh и relay вместе, а не что-то одно

Чисто mesh-сеть (как в старых walkie-talkie-приложениях) отлично работает, пока все, до кого нужно достучаться, в паре Bluetooth-прыжков. Чисто relay-мессенджер работает где угодно при наличии интернета, но останавливается, как только его нет — при стихийном бедствии, в тоннеле метро, на митинге, где режут мобильную сеть, или просто в подвале без сигнала.

`GossipRouter` в Rlink относится к обоим транспортам как к равноценным. Сообщение рассылается всем BLE-mesh-пирам и relay-соединениям, которые сейчас есть у устройства, дедуплицируется через кэш уже виденных пакетов и ограничивается счётчиком хопов (TTL) — одно и то же сообщение может прийти тремя разными путями, и это нормально, доставится оно всё равно один раз. Логика маршрутизации — в [`lib/services/gossip_router.dart`](lib/services/gossip_router.dart), сторона relay — в [`relay_server/`](relay_server/).

## Архитектура в двух словах

```
┌─────────────┐        BLE / Wi-Fi Direct        ┌─────────────┐
│  Rlink app  │◄────────────────────────────────►│  Rlink app  │
│ (устройство │                                   │ (устройство │
│      A)     │                                   │      B)     │
└──────┬──────┘                                   └──────┬──────┘
       │                  WebSocket                      │
       └───────────────►┌───────────┐◄───────────────────┘
                         │   relay   │
                         │  сервер   │  (zero-knowledge — видит
                         └───────────┘   только шифртекст и маршрут)
```

- **Клиент** (этот репозиторий): Flutter-приложение под все четыре нативные платформы плюс web. `lib/services/` — транспорт (`ble_service.dart`, `relay_service.dart`, `gossip_router.dart`), криптография (`crypto_service.dart`, `double_ratchet.dart`) и хранилище; `lib/ui/` — интерфейс.
- **Relay-сервер**: небольшой Dart WebSocket-сервер с минимумом зависимостей ([зеркало: `rlink-relay`](https://github.com/MihailKashintsev/rlink-relay), также лежит внутри этого репозитория в [`relay_server/`](relay_server/)), маршрутизирует пакеты по публичному ключу и держит офлайн-почтовый ящик. У него никогда нет ваших приватных ключей, и он никогда не расшифровывает сообщения. Как поднять свой — [`relay_server/SELF_HOSTING.md`](relay_server/SELF_HOSTING.md).
- **Web-сборка**: зеркалируется в [`rlink-web`](https://github.com/MihailKashintsev/rlink-web) для хостинга на GitHub Pages.
- **Подписанные релизные сборки**: публикуются в [`Rlink-releases`](https://github.com/MihailKashintsev/Rlink-releases) через CI при каждом версионном теге.

## Возможности

- Личные чаты, группы и каналы вещательного типа
- Аудио/видеозвонки (WebRTC, с возможностью поднять свой TURN-сервер для обхода NAT)
- Система стикеров из трёх форматов: растровые (`.rls`), собственная мини-студия векторной анимации (`.rlv`) и импорт Telegram `.tgs` — плюс встроенные инструменты удаления фона и превращения фото в вектор
- Наборы кастомных эмодзи, подсказки стикеров/эмодзи по вводу эмодзи в поле сообщения
- No-code конструктор ботов (правила → сгенерированный Python, запускается локально) и каталог ботов на relay
- Связка устройств (зеркалирование аккаунта на второе устройство) и перенос аккаунта на новое устройство
- Опциональный бэкап истории каналов/групп в Google Drive
- Опциональный Rlink Premium (цвет ника и другие функции) через самостоятельно развёрнутую интеграцию с ЮKassa — полностью опционально, ядро мессенджера от этого не зависит

## Модель безопасности

- Идентификатор: Ed25519 (подпись) + X25519 (обмен ключами), генерируются и хранятся на устройстве.
- Личные сообщения: Double Ratchet ([`lib/services/double_ratchet.dart`](lib/services/double_ratchet.dart)), как только оба клиента его поддерживают, иначе — откат на схему с подписанным свежим эфемерным ECDH на каждое сообщение. Точный вырез по сравнению с полным X3DH-рукопожатием описан в doc-комментарии файла.
- Сигнализация звонков шифруется и подписывается так же; сам медиапоток защищён встроенным в WebRTC DTLS-SRTP, так что даже вредоносный TURN-relay не может его прочитать.
- Коды безопасности позволяют двум контактам убедиться, что они действительно общаются друг с другом, а не с подменённым MITM-ключом.
- Relay намеренно сделан «глупым»: аутентифицирует соединения по публичному ключу, маршрутизирует шифртекст и складывает очередь для офлайн-получателей — даже при полной компрометации ему нечего слить, кроме метаданных (кто онлайн, размеры/тайминг пакетов).

Это не аудированная профессионалами криптографическая реализация. Относитесь соответственно, особенно к коду Double Ratchet — это оригинальная разработка, а не обёртка над проверенной временем библиотекой.

## Известные ограничения

- Пока нет инфраструктуры pre-key по X3DH — см. пометку о вырезе выше.
- Федерация между разными relay-серверами пока только клиентская (клиент может достучаться до контакта на другом relay, тоже подключившись к нему напрямую), а не настоящий протокол между серверами — два контакта, у которых оба свои разные relay (ни один не официальный), пока не смогут связаться друг с другом.
- На iOS нет push-уведомлений при полностью закрытом приложении (нет аккаунта Apple Developer для выпуска APNs-ключа) — BLE-mesh и web push при этом работают.
- Это проект одного человека, который развивается открыто по ходу дела; некоторые места отполированы лучше других, а часть ограничений (отмечены в комментариях кода) — осознанный вырез объёма, а не недосмотр.

## Быстрый старт

```bash
flutter pub get
flutter run
```

Нужен Flutter SDK (минимальную версию см. в `pubspec.yaml`) и, для звонков, TURN-сервер — как поднять свой relay+TURN см. [`relay_server/SELF_HOSTING.md`](relay_server/SELF_HOSTING.md). Без TURN-учётных данных, переданных через `--dart-define`, звонки всё равно работают между пирами, которые могут соединиться напрямую (только через STUN).
